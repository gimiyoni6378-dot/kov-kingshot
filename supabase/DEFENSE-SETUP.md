# 성벽 지키기 포인트 연결

GitHub Pages는 화면만 배포합니다. 아래 두 설정까지 끝나야 로그인 회원이 게임을 시작하고 보상을 적립할 수 있습니다. 비밀번호·secret 키를 사이트나 채팅에 입력하지 마세요.

## 1. SQL 실행

Supabase 프로젝트 → SQL Editor → New query에서 `003-defense-rewards.sql` 전체를 붙여넣고 Run을 누르세요. 기존 `gallery.sql`, `002-points.sql`이 실행된 프로젝트를 기준으로 합니다. 처음 설치하는 프로젝트라면 세 파일을 번호 순서대로 실행하세요. 이후에도 002를 다시 실행한다면 003까지 실행해야 합니다.

## 2. 게임 검증 함수 배포 (대시보드)

1. Supabase 프로젝트 → Edge Functions → Deploy a new function → Via Editor를 선택합니다.
2. 함수 이름을 정확히 `defense-reward`로 입력합니다.
3. `defense-reward-dashboard.ts` 전체 내용을 기본 `index.ts`에 붙여넣습니다. 이 파일에는 게임 엔진과 검증기가 모두 포함되어 별도 파일이 필요 없습니다.
4. Deploy function을 누릅니다.
5. 함수 설정에서 **Verify JWT with legacy secret** 옵션을 끕니다. 최신 키 형식도 지원하도록 함수 코드 내부에서 `auth.getUser(token)`으로 매 요청의 로그인 토큰을 직접 검증합니다. 로그인 검증은 유지됩니다.
6. Supabase가 기본 제공하는 `SUPABASE_URL`, `SUPABASE_SERVICE_ROLE_KEY` 환경변수를 사용합니다. 이 키를 GitHub에 넣거나 브라우저에 전달하지 않습니다.

CLI를 사용할 때는 저장소 루트에서 `supabase functions deploy defense-reward --project-ref vapibdrcmcmnxqutwidy --no-verify-jwt`로 배포할 수 있습니다. 두 방식 중 하나만 사용하세요.

## 3. 동작 확인

- 로그인하지 않은 상태에서 `/defense.html`을 열면 로그인 안내가 나오고 모집·전투가 막힙니다.
- 로그인 후 첫 시작은 병사 0명·200골드입니다.
- 5단계 클리어 후 ‘종료하고 포인트 받기’를 누르면 30P, 6~8단계는 40P, 9단계는 50P, 10단계 완주는 100P가 한 번 적립됩니다.
- 실패하면 마지막으로 클리어한 단계 기준으로 자동 정산합니다. 예: 6단계에서 실패하면 5단계 클리어 보상 30P입니다. 4단계 이하는 0P입니다.
- 단계별 보상을 누적 지급하지 않습니다. 한 판 최고 클리어 기준의 최종 보상입니다. 다른 판을 플레이하면 다시 받을 수 있습니다.
- 전투 중 종료 정산은 막고, 웨이브 사이에 종료할 수 있습니다. 24시간 지난 판은 만료됩니다.
- 마이페이지 맨 위 ‘내 보유 포인트’와 기록의 ‘성벽 지키기 보상’을 확인하세요.
- 네트워크 오류 시 결과창에서 다시 시도하세요. 웨이브를 끝낸 기록과 정산 중이던 기록은 계정별로 브라우저에 보관하여 새로고침 후 재연결할 때 재시도합니다. 보관 데이터를 지우거나 다른 기기로 옮기면 미전송 기록은 복원할 수 없습니다.

## 검증과 운영

브라우저의 점수·클리어 숫자를 신뢰하지 않습니다. 서버가 합법적인 모집·회수·웨이브 시작 기록을 같은 엔진으로 60Hz 재실행하여 클리어 단계를 계산합니다. 한 판의 DB 행을 잠그고 원장에 유일한 이벤트 키로 적립하므로 동시 요청·재시도가 중복 포인트를 만들지 않습니다. 다른 회원의 판을 제출할 수 없고, 원장 쓰기 및 최종 적립 RPC는 브라우저에서 실행할 수 없습니다. 실제 경과 시간보다 지나치게 빠른 제출도 거절합니다.

반복 플레이의 횟수 제한은 없습니다. 합법적인 전략을 자동 실행하는 봇을 구별하는 기능은 포함하지 않습니다. 엔진이나 보상 규칙이 변경되면 `node scripts/build-defense-function.mjs` 실행 후 Edge Function도 다시 배포하세요. 진행 중인 판과 호환되지 않는 엔진 변경에는 replay/run 버전을 함께 올려야 합니다.

Tests: `node tests/defense-rewards.mjs`. SQL 권한·중복·계정별 적립 테스트는 `tests/defense-rewards-sql.mjs`(PGLite 경로 지정)에서 실행합니다.

## 난이도 강화 업데이트 (기존 설치 완료 시)

SQL은 다시 실행하지 않습니다. Edge Functions → 기존 `defense-reward` → Code에서 `index.ts` 내용을 최신 `defense-reward-dashboard.ts` 전체로 교체한 뒤 Deploy updates를 누르세요. 기존 JWT 설정은 유지합니다. 새 함수를 추가로 만들지 않습니다.

최신 함수는 GET 응답에 `balance_version: 2`를 반환합니다. 사이트는 이 값을 확인한 뒤 게임을 열기 때문에 기존 함수 상태에서는 ‘난이도 업데이트를 준비하고 있어요’ 안내가 나옵니다. 배포 후 게임에서 다시 연결 또는 새로고침하세요. 이전 업데이트 전에 시작한 판의 저장 기록은 이전 엔진으로 정산하고, 이후 새 판부터 강화된 규칙을 사용합니다.

## 보병3열 공격·화염 마법사 업데이트

SQL 재실행 없이 기존 defense-reward 함수의 index.ts를 최신 defense-reward-dashboard.ts 전체로 교체하고 Deploy updates 하세요. 최신 GET 응답은 balance_version3입니다. 이전2였던 함수로는 새 게임이 열리지 않습니다. 사이트를 새로고침하면 새 규칙이 적용됩니다.

서버가 소유권을 확인한 run UUID로 히든 확률 시드를 계산합니다. 클라이언트가 전송한 히든 등장 여부나 임의 시드를 믿지 않습니다. 이전 버전 플레이 기록도 해당 버전 엔진으로 검증합니다.
